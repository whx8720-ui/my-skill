# 确认与迭代工作流

## 目的

帮助用户先判断“谁在什么页面完成什么任务，组件如何配合”，再判断真实页面是否正确。第一次先确认产品结构，后续通过小范围组件预览收敛修改。确认流程适用于具体产品原型；用户要求编辑本技能本身时，不把它误当成待确认的产品需求。

## 1. 读取不同输入

| 输入类型 | 应提取 | 不可默认 |
|---|---|---|
| 粗浅想法 | 要解决的问题、角色、关键对象、主流程、最小页面集合 | 没提的角色、审批、收费或复杂后台都是必须功能 |
| 完整说明书 | 角色权限、业务规则、页面与状态、字段、验收条件；查内部矛盾 | 篇幅长就不存在遗漏，或文档里的流程已经被本轮确认 |
| 页面字段思维导图 | 页面层级、分组、字段、动作与关系，保留源节点名称 | 树节点就是页面、字段顺序就是最终布局、所有字段可编辑或必填 |
| 截图／既有原型与修改描述 | 页面身份、组件边界、当前行为和期望变化 | 截图能证明实际行为、视觉相似就是同一个组件 |

能从材料获取的事实先读，不重复让用户填写。材料不可读时说明具体缺失范围，只询问当前最影响流程的一项。对于“支持分点”“提供试用”“详情时间”等含糊表述，保留原话并标为待确认；不能自动把分点理解为多任务、把试用理解成试听或免费额度。

第一次回应应能给出初步链路与页面结构（信息足够时），缺口一次只问一个。不要为了完整而无限追问颜色、边距等已有规范决定的事项；没有关键业务阻塞时，将低风险默认值明确放进方案等待整体确认。

## 2. 先看组件，再写方案

依次检查：本项目已批准组件 → 技能组件索引与 Vue 封装 → 对应 HTML 示例 → Element Plus 基础组件。

- 说明组件是直接复用、参数扩展、由旧 HTML 迁移，还是需要新增。
- 给用户看的说明引用中文组件名即可，附来源标识；别让用户只能读懂文件路径或 Vue props 才能确认。
- 源文件只证明已存在的实现，不证明其正确性。按索引指出静态样例和缺失行为。
- 已有批量输入组件的编号条目、键盘行为可复用到文案输入，但链接格式校验不能带过去。
- 页面上已有的同名组件如果规则不同，应说明变体／参数，不擅自统一业务规则。

组件复用状态可写为：“批量文案输入【复用：批量输入框；迁移为 Vue】”。同一通用组件在多个页面复用，页面中的用途与参数仍分别说明。

## 3. 角色核心交互链路

每个角色分别描述：入口 → 核心动作 → 对象或状态变化 → 下一页面／结果。动作不能只有名词，分支不能用斜杠掩盖差异。

用户给的管理员／普通用户视频工作流是表达示例，不是所有项目的固定范围。只有本次需求包含对应角色和动作才采用：

- 管理员：产品管理 → 新建产品 → 上传归属该产品的素材 → 查看处理／打标结果 → 调整标签或执行带理由的删除 → 更新可用素材。
- 普通用户：信息输入 → 选择参数 → 提交生成 → 任务列表查看进度 → 完成后进入校准 → 调整素材或擦字幕 → 确认结果 → 下载。

还应明确：

- 管理员创建的产品／素材在哪一步被普通用户使用，谁可见、谁可编辑；材料没说的权限标待确认。
- 提交失败回哪里、是否保留输入；处理失败如何重试；没有可用素材如何返回补充。
- 校准保存是否生成新版本、是否覆盖已有结果；下载入口由哪个状态开放。此类业务后果不自作主张。
- 从详情返回列表保留哪些筛选、分页或选择；跨页传递的是哪个产品／任务／素材 ID。

可用一张小型 Mermaid 图辅助，但文字链路必须足够清楚，不用图替代规则和分支说明。

## 4. 逐页组件说明

按页面实际从上到下排序；同一横排从左到右；详情抽屉、确认弹窗单独列在触发组件下并说明其内部顺序。页面至少说明角色、目的、入口、出口及核心动作。

核心组件用“名称（复用来源）：内容／操作＋关键规则＋操作结果”的短段落表达。尽可能覆盖以下相关信息，而不是每个控件机械填十几列：

| 内容 | 何时需明确 |
|---|---|
| 字段及顺序 | 表格列、表单分组、详情区块；展示还是编辑 |
| 必填与默认值 | 会影响提交、筛选结果或用户理解时 |
| 选项与搜索 | 下拉来源、单／多选、可输入搜索、清空、预览／试听 |
| 校验和限制 | 数量、长度、时长、格式、权限；未知阈值不能编造 |
| 操作与反馈 | 点击行为、校验失败、处理过程、成功后的数据变化 |
| 依赖与联动 | 产品决定可选素材，筛选影响列表，列表选择影响详情等 |
| 状态 | 本组件适用的初始、空、加载、失败、禁用、超限与成功 |
| 返回与撤销 | 弹窗取消、离开未保存、返回保留内容；仅列本次必要场景 |
| 角色差异 | 谁能看、谁能改、谁能执行危险操作 |
| 复用证据 | 对应组件及规则、使用原样还是参数化扩展、新增差异 |

**完整度的判断是能否明确用户操作的结果，不是文档长度。** 一个“详情”按钮后面应该能找到详情容器及内容，一个“生成”按钮后面应该能找到新任务、状态和后续入口。

### 页面说明写法示例

以下仅演示表达结构，业务内容仍需来自当前用户材料：

信息输入页（普通用户；提交后进入任务列表）

1. 批量文案输入【复用：批量输入框】：编号条目，Enter 到下一条／末尾新增，Shift+Enter 条内换行，过滤空项；文案分点与任务拆分的对应关系若未说明，标“待确认”。
2. 生成参数【组合：Element Plus 可搜索下拉】：按需求列真人口播、字体、配音等字段及选项；“试用”具体是试听、字体预览或生成样例，未明确前不实现为某一种。
3. 提交区【复用：主次按钮规范】：校验输入和必选项，显示本次任务数量，提交后创建对应模拟任务；参数缺失、提交中和失败保留输入有具体反馈。

任务列表页

1. 筛选区【复用：业务日期范围＋人员筛选】：任务记录可含当天，人员可搜索，任务名搜索；明确默认条件、重置规则及与分页联动。
2. 任务表格【复用：Element Plus 表格】：按确认顺序列任务名称、创建时间、状态、操作；详情为操作入口还是独立列按用户材料确定。不同状态的操作是否可用写清。
3. 任务详情【待确认容器：抽屉或详情页】：依次显示基础配置、操作／时间记录、片段详情；从该行进入，展示该任务数据，返回保留列表上下文。

不能把示例中的“状态”“抽屉”等建议默认为用户已同意；标注建议，随方案整体确认。

## 5. 首次确认和版本

在当前项目维护：

- `prototype/interaction-spec.md`：当前待确认或已确认方案，含版本、来源、链路、页面组件、规则、待确认项。
- `prototype/workflow-state.md`：当前阶段、方案版本、已确认范围、用户确认原话或会话依据、待确认事项、主工程入口。
- `prototype/component-map.md`：开始实现后维护页面 ID／组件 ID → 文件 → 复用关系。较小项目可合并进方案，避免无用文件。

页面与核心业务组件使用简短稳定 ID，如 P01、P01-C01；用于对齐变更，不给每个标签和图标编号。小修改保持 ID，页面重排不必重编号。

阶段示例：`drafting-spec` → `awaiting-spec-confirmation` → `building` → `ready` → `previewing-change` → `awaiting-component-confirmation` → `integrating` → `ready`。

确认请求：“请确认这版角色链路和各页面从上到下的组件说明；确认后我再生成原型。”用户“确认／没问题／按这版做”等，在有明确单一版本的上下文中有效。若有多个候选，只确认其指定版本；批注和修改意见不是自动确认。

涉及核心权限、提交后果、删除影响等关键未知未解决，不应声称方案完整或已确认。非关键默认值可随方案整体确认；用户明确允许某区域占位，记录授权后按范围继续。部分页面确认可只实现这些页面，不能连带实现未确认的关键分支。

用户要求修改方案时更新版本并重述受影响部分；未受影响的已确认规则继续有效。方案确认后新需求改变链路、权限或数据结果，应先确认对应方案增量，不重开整个项目的问卷。

## 6. 组件修改与独立预览

本节适用于新增组件或改变视觉布局。只改文案、下拉选项、交互逻辑时，先列改动清单，确认后直接修改，不走预览流程。

1. **定位**：从当前页面、截图、组件 ID、字段名称定位主工程；写明页面与组件、修改目标、共享引用范围。两个页面都存在相同名称且无法判断时先问一个问题。
2. **界定范围**：单页特例优先通过局部参数或变体实现；全局主题、共享状态或组件变动必须列出所有受影响页面。用户仅说“把这里改一下”不是全局改造授权。
3. **隔离候选**：在 `prototype/changes/C01/` 等独立目录准备候选源码、最小宿主和模拟数据，不修改已交付主工程的源码／共享样式／锁文件，也不覆盖主 dist。必须修改配置或依赖时先在候选副本中处理。
4. **生成预览**：使用与主工程相同的 Vue／Element Plus／主题，预览当前修改组件及必需上下文。仅组件难以判断联动时展示最小相关组件组；与整页共享同一份候选源码，不能另写一个看似相同的假演示。
5. **交付候选**：提供 `页面名-组件名-v2.html` 与资源包／实际可用预览地址，并简述修改前后、受影响页面、查看操作、已验证和未验证项。明确“尚未合并整页”。按 [HTML 交付约定](engineering.md#html-交付与组件预览) 处理文件依赖。
6. **等待确认**：默认停在 `awaiting-component-confirmation`。用户要求继续调整时更新候选，给新版本；旧版本确认不覆盖新版本。用户明确授权预览后直接合并可按其新授权跳过本次停点。
7. **合并**：确认所见预览对应当前候选，检查主工程自候选创建以来有无修改。把已确认 Vue 组件与必要集成改动合并，保留同一输入／输出事件契约、模拟数据联动和主题；从主工程重新构建完整 HTML，不粘贴压缩后的 HTML/JS。
8. **回归**：验证被改组件、调用它的已授权页面，以及相邻链路：筛选→列表、选择→详情、确认→数据更新等。组件预览通过不代表整页集成通过。记录主版本、整页入口与集成结果，保留可恢复的原版或 Git 差异。

候选必须记录：基于哪个主版本、哪些文件／组件、哪些页面、候选版本、预览入口、是否已获确认。可用 Git commit 或文件哈希标识主版本，不强迫非 Git 项目创建仓库。主工程发生实质冲突时更新候选重新展示；机械导入路径适配且不影响结果时无需再次确认。

## 7. 组件沉淀

项目内可将已确认的通用实现登记到组件映射，后续先复用。保持业务参数与视觉令牌分离，避免全局修改组件时更改所有页面的业务约束。不要自动把客户／项目特定规则或数据写进全局 `mydesign` 技能；用户明确要求全局沉淀时再更新对应索引与资源。

## 8. 交付前自查

- 是否在页面说明前查过已有规则和组件，而不是先设计一套新的？
- 是否区分用户事实、继承规则、建议和待确认？
- 每个主动作是否有数据结果、状态和去向，每个关键弹层是否有入口／提交／取消？
- 是否遵守当前阶段的确认范围，没有偷跑生成或合并？
- 预览是否用同一份候选源码、能打开，整页是否确实包含用户确认的那版？
- 确认记录能否让下一轮继续工作，而不重问已经确认的事项？

交付时在回复中逐项写出以下核对结果：

- 主色是否为中性蓝 `#0070f3`；已有页面不符合时是否已提醒用户。
- 提示与警示是否使用样张样式（如警示 `.note.is-warn`）。
- 同类功能是否复用了组件库中的对应组件。
- 改动交互规则时，是否列出关联规则并等待用户确认。
- 是否在浏览器中验证；未验证时写明原因。
